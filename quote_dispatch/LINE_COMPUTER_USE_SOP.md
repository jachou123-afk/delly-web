# LINE 商品廣告 Computer Use 執行 SOP

版本：1.1｜更新：2026-09-17｜適用網站：V87.11 的第二次檢查與快速發送工作台

正式來源：本文件在 [jachou123-afk/delly-web 的 main 分支](https://github.com/jachou123-afk/delly-web/blob/main/quote_dispatch/LINE_COMPUTER_USE_SOP.md)。

## 目的與執行邊界

解析與報價 → **發文前第二次檢查** → 凍結原圖文 → 同一 LINE 聊天室依序「圖＋文」 → 實際看到結果 → 完成並下一則。

加速的是第二次檢查之後的執行，不省略第二次檢查，也不把「已準備／已複製／已按傳送」當成已發。工作台沿用個人 LINE 的可見介面，不接 LINE@ 或 Messaging API。

本文件是操作規範，不是新的發送授權。只要求讀取、修改 SOP 或檢查時，不發送 LINE。本次使用者另行交付發送／續作任務，且批次、聊天室與範圍清楚後，才開始執行。

**「重新執行」一律解釋成重新查核後接續未完成部分，不是整批從頭重發。**

執行當下的工具文件、權限與確認要求優先於本 SOP。若工具要求發送前另行確認，依規則辦理，不能用本文件跳過。不可因追求速度停用驗證、略過發送結果確認，或改用未授權的 LINE API／隱藏介面。

## 1. 換電腦／重新開始前：先讀最新版

1. 從 GitHub `main` 讀取本文件及根目錄 `HANDOFF_STATE.md`；記錄本次 SOP 版本與遠端提交 SHA，不只依賴聊天摘要或舊下載副本。
2. 使用本機 checkout 時，透過允許的 repository／terminal 工具先 fetch、檢查遠端與工作目錄，再以 fast-forward 更新。若有本機未提交修改或分支分歧，保留並回報；不 reset、不覆蓋其他電腦的工作。不要用 Computer Use 在 Windows 終端或檔案視窗執行命令。
3. 讀取執行電腦目前可用的 Computer Use／Browser Use 技能與操作文件。確認能控制**實際要發送的 LINE 視窗**；原生控制不可用時，不假裝已連線，也不擅自改用別的 LINE 官方帳號。
4. 打開 [正式網站](https://delly-web-eczbucrrkrr7caoe568w4w.streamlit.app/)，確認畫面具備本文件所列的整批操作入口。不同版本導致入口不符時，先查最新文件，勿套用舊座標。
5. 在「發送管理」按一次「重新載入雲端」，核對批次 ID、名稱、目標聊天室及最新狀態。批次名稱中的「9 款」等字樣不是目前待發數量；以最新明細為準。
6. 同一批次同一時間只讓一台電腦／一個執行者傳送。確認前一台已停止；若不能確認交接，先停止新發送。網站的版本衝突保護**不是 LINE 發送鎖**，不能阻止兩台同時發出相同訊息。

## 2. 一次釐清這批實際要做的範圍

目標以本次使用者授權及批次保存值為準。常用選項是「周俊安」與「【利潤10%】 自動排廣告群組」，不能因為有預設值就自動選它。舊群組別名僅供辨識資料，不是略過 LINE 實際群組名稱／成員確認的理由。

對照「待處理」、原有雲端紀錄、前次交接及 LINE 實際訊息後，建立本次工作清單：

| 情況 | 這次應做的事 |
|---|---|
| 圖片、文案均已在正確聊天室確認 | 不再發送；若雲表未登記，只補登紀錄 |
| 圖片已確認、文案未發 | 只補本款文案，不重發圖片 |
| 文案已確認、圖片未發 | 只補本款缺少的圖片，不重發文案 |
| 無確認紀錄，且查核未見已發訊息、前次沒有未釐清的發送嘗試 | 納入待發清單 |
| 雲表無紀錄，但可能已發／發送中斷／有重複紀錄 | 先查 LINE 與前次執行紀錄；無法釐清時暫停該款，不盲目重試 |
| 本批排除、原因待釐清、資料有問題 | 不加入待發清單；記錄具體缺口，不自行解除排除或猜測商品資料 |

「尚無發送確認紀錄」不等於「一定沒發」；只用文字搜尋不到，也不足以證明圖片未發。核對相關日期範圍、圖文順序、品號與完整內容。不能把其他聊天室或不同版本的廣告，當成本批已發證明。

## 3. 圖文一次準備，不在每款發送時重新抓圖

1. 在「本輪工作台商品（預設全選）」只保留本次要發的商品。工作台只接收整組待發；部分完成／結果不明走原單款處理，已發只補登，不再安排傳送。
2. 執行人只填一次（由 Computer Use 查驗就如實填寫，不假稱使用者親自核對），確認正確聊天室、未發範圍、前一台已停止，按「第二次檢查並開啟工作台」。程式重讀批次版本、雲表來源、成本公式與原始依據、售價／單位／文案、同聊天室其他批次及原圖校驗。任何阻擋未通過都不能進入卡片。沿用舊版已明示接受的缺原文限制時，仍顯示缺原文數量，不宣稱原文已核實。
3. 成功後可在「一次下載全輪原圖與文案／操作規則」取得「下載本輪已檢查圖文包」，也可從卡片取本款原圖及複製完整文案。原圖一次備妥，逐卡不再讀 NAS 或重算。不要在仍處理中連按產生；首次備圖仍受 NAS／網路速度影響。
4. 透過執行環境允許的檔案功能，將 ZIP 解壓至本次專用目錄，不覆蓋前次素材。若工具不能存取下載檔／不能把圖片交給 LINE，回報實際阻礙，不自行安裝工具或改走未核准方法。
5. 以 `發送順序與說明.txt` 及 `NNN_品號/` 資料夾建立一次性的順序清單；先備妥各款 `圖片01.*`、後續圖片及 `文案.txt`。工作台每卡提供全部凍結原圖及完整文案；若使用舊整批工具補部分圖文，其下載包只含缺少部分，須對照既有紀錄。
6. 檢查品號、圖片張數、圖片內容與文案配對。不用截圖代替原圖，不任意重新壓縮、改售價、改規格或改字。
7. `整批文案.txt` 是整理用副本。實際 LINE 預設仍是「本款圖片 → 本款文案 → 下一款」，不得把全部圖片先送完，再將不同商品文案合成一則，以免圖文錯配。
8. 超過下載包原圖 64 MB 限制時，才拆成較小素材包；保持同一批次與順序，不為每款另建批次。尚未確認／未準備好的商品不能發送。
9. 第二次檢查是當時快照，不是持續監控雲表。價格／來源／規格／圖片／文案／目標有變動，或換人換機、中斷結果不明，先按「暫停／有問題，返回處理」。修正並重新確認受影響商品後，重新選取／檢查；未受影響且仍在有效工作台的商品，不逐款重查。重新載入、切换批次、另一台更新或保存失敗均不直接沿用舊卡片。

## 4. 在 LINE 連續處理，保留必要確認

### 開始一次

- 從工具回傳的視窗／分頁中選定唯一的目標 LINE，查看目前登入帳號、聊天室標題；同名群組需用成員等可見資訊辨識。
- 檢查訊息輸入框沒有他人未送出的草稿。遇到不明草稿，不刪除、不覆蓋、不連同本批送出。
- 建立本次執行紀錄，欄位見第 5 節。使用本輪已準備的素材或卡片，不重新找商品、重新載 NAS 原圖、重填核對人或重跑報價。

### 每款的小循環

1. 確認本款品號、需要補的部分，以及目前仍在正確聊天室。
2. **圖片：**用目前工具明確支援的方法附加本款原圖；若支援多檔選取且已驗證排序，可一次加入同款全部缺少圖片。先看預覽張數／內容，再送出。不要把檔案路徑當作商品圖片文字貼出，也不要假定所有 LINE 版本都支援圖片剪貼簿。
3. 查看圖片訊息確實出現在聊天室、沒有傳送中或失敗狀態；記錄已確認張數。只送出部分圖片時，記錄哪些已出現，不把「本款全部圖片」標為完成。
4. **文案：**確認焦點在訊息輸入框，使用支援的整段文字輸入／貼上方法，一次帶入本款完整文案，不逐字模擬鍵盤。不臨時切換編輯器逐行複製。
5. 查看輸入框內容的品號、售價、單位與換行，確認不是貼進搜尋框；依實際介面的傳送方式送出，不猜測 Enter 是換行還是傳送。
6. 查看本款文案訊息確實出現、沒有失敗狀態，核對它與本款圖片相鄰。工作台按一次「完成並下一則」；程式寫入本款圖文查驗結果，雲端讀回成功才前進。按鍵本身是執行人的實際查驗聲明，不是 LINE API 回執。登記時間不冒充 LINE 訊息時間；有訊息時間／其他可見依據可填選填欄位。若採下述連續執行模式，則記入工作紀錄，最後整批補登。

只發缺少的部分。每次傳送嘗試前先將該部分記為「準備送出／結果待查」，看到成功畫面才改為「已確認」。工具逾時或回應不明時，不能用再次按傳送來測試。

### 減少等待的做法

- 保留已取得的目標視窗／分頁控制物件；沒失效就不重新列出全部視窗、重新尋找聊天室或重建工具環境。
- 每一步只取下一個判斷需要的畫面資訊。文字足以確認時不額外要求全螢幕截圖；圖片辨識、焦點不明或版面改變時才取必要截圖。不要把同一張截圖重複讀取／輸出。
- **遵守當下工具的觀察—操作—更新規則。**原生 Computer Use 若要求一次操作後刷新，就照做；瀏覽器只有在其文件允許時才合併可確定的動作。不可用舊座標跨多個商品盲送，也不可省略焦點及傳送結果確認。
- 優先等待「預覽出現／訊息已出現／上傳完成」等可見條件，不為每次操作固定多等數十秒。仍無變化時採有限等待與檢查，不高頻重複刷新或無限重試。
- **工作台模式：**發圖＋發文＋實際查驗後，按一次完成並下一則。不在圖文中間切回登記，不重跑驗算或下載同一張圖。**Computer Use 連續執行模式：**若切回登記成本較高，可在第二次檢查通過並下載凍結包後留在 LINE 連續做，逐款保存實際可見依據，最後依第 6 節整批補登；不可省略第二次檢查、逐款結果查驗或中斷紀錄。兩種模式不交錯重發同一款。
- 收到新指示、視窗被使用者接管或目標改變，立即暫停，重新確認範圍。

## 5. 中斷與跨電腦接續：防止重複發送

本次執行者維持一份工作紀錄；可以使用執行環境已支援的工作檔，不依賴模型記憶。它是續作線索，不是雲表正式回執，也不可把私人 LINE 紀錄／圖片／商品包提交到公開 GitHub。

記錄欄位：

```text
執行 ID／執行電腦：
SOP 版本／GitHub 提交：
批次 ID／批次讀取時間：
目標聊天室／辨識依據：
素材包與準備時間：
品號｜圖片嘗試／已確認張數與檔名｜文案嘗試／已確認｜LINE 時間／可見依據｜雲表是否已保存
最後已確認品號：
結果待查品號與原因：
```

- 計畫內的結束、交接或長時間暫停：先把有證據的完成／部分完成／結果不明狀態保存至原雲表，確認保存成功，再交接。執行紀錄未同步前，不能稱跨電腦接續已就緒。
- 崩潰、斷線或強制中斷：下一台先重新載入雲表，再查 LINE 與能取得的上次紀錄。**即使雲表仍顯示未登記，也不能從第一款直接重送。**
- 沒有上台紀錄，或訊息範圍無法確認：將受影響商品列為結果待查，先回報缺口。不可憑「應該沒有發出去」補送。
- 如已在發送中的素材發現來源變更，不重新產生文案後混著舊版續送；先停止受影響商品，保留已發事實與版本差異，待使用者決定如何處理。

## 6. 保存與最後對帳

工作台模式已每款保存，不再把已完成款批次重登；完成本輪後展開「進度清單／既有批次補登／異常與對帳」核對全批，仍有重複／未處理異常時不能結案。保存只讀本批版本鏈及短索引，不重拉全部批次內容，仍保留版本衝突與寫後讀回。

以下適用連續執行模式，或已有 LINE 實際證據但雲表尚缺紀錄的補登：

1. 回到 Streamlit「發送管理」，按「重新載入雲端」，重新核對批次 ID／聊天室與最新紀錄，避免拿舊畫面覆蓋另一台的進度。
2. 在「本次一起處理的商品」**只選圖片與文案都已在正確聊天室實際確認、但雲表仍缺紀錄的商品**。預設全選不是已完成證明。
3. 在「已在 LINE 發完？一次登記所選商品」填實際執行／核對人及訊息時間範圍、品號與核對依據。若由 Computer Use 查驗，要如實記錄為 Computer Use 查驗，不假稱使用者親自核對。
4. 確認以上結果後，按一次「一次保存所選商品的發送紀錄」。只有全批確實完成且沒有異常，才使用「若全批已核對且無異常，同時完成對帳」。
5. 只完成圖片或只完成文案的商品，使用「只處理單款／部分圖文／異常」保存實際完成部分；只有部分圖片成功或結果不明時，登記待確認並註明已見張數、檔名及時間，不勾整款圖文完成。
6. 保存成功後讀回核對數量及品號；網站無紀錄／報錯／逾時不代表 LINE 沒發。遇版本衝突先重讀、合併實際缺少紀錄，不再次發送 LINE 來補雲表。
7. 最後回報：本次已確認完整商品數、部分完成、待查／未處理品號及原因、雲端保存是否成功。沒有完全查驗與保存的，不宣稱整批完成。

## 7. 下次量測速度，不憑感覺判斷

用前 3 款正常商品作為本次已授權發送的一部分，記錄以下時間，不額外發測試廣告：

- 整批素材準備時間（一次性，另列，不攤成每次貼上的耗時）。
- 每款：附圖準備、LINE 圖片送出至可見確認、文字輸入、文案送出至可見確認。
- 畫面觀察／工具往返的次數與耗時；工具呼叫間的等待另列，不能算成 LINE 上傳。
- 每款完成並下一則的保存時間，或最後整批雲表回寫時間（依所用模式）。

只在工具有記錄時報告精確時間；缺少計時就標示未量測。正常就接續本次授權範圍，不每 3 款要求重新授權；若當下工具要求額外確認則依其規則辦理。沒有實測前，不承諾固定加速倍數。
