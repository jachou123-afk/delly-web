# 微信圖文核對、解析與雲表貼圖作業規範

版本：1.6｜更新：2026-10-12

正式流程：下載原始對話與附件 → AI 核對圖文 → 例外由使用者確認 → 解析並保存半自動表 → Computer Use 貼圖 → 重新開啟雲表核對。

## 多品村固定決策（2026-10-11 文字優先；2026-10-12 同貨號不同商品及外盒差異規則）

本節優先於舊批次的逐款暫緩紀錄，適用目前尚未處理及往後的多品村商品；不追補使用者已跳過的舊日期，也不無故改寫已完成商品。

- **文字優先**：先確認圖文是同款。尺寸、重量、顏色、裝箱／端盒數量等圖文差異，採完整原文中明確且自身一致的數值與單位；保留原圖、原文及差異，不反覆詢問。範圍尺寸照原文保留，不捏造成長寬高；不把「採大數字」套用到其他商品。
- **外盒差異依文案**：使用者在YX-Y12外盒型號／展示圖疑點再次確認「依文案為主」。當主圖標示的完整型號、主商品外觀與原文一致，來源配對唯一時，僅外盒印刷型號或展示圖不同，採原文型號及規格並保留外盒差異註記，不再因同類外盒差異重問。YX-Y12與YX-Y12-2依此通過；原圖仍完整保留，不改圖、不宣稱实际出貨包裝已驗證。此規則不涵蓋主商品本身型號／外觀與文案衝突、非唯一配對或原文內部矛盾。
- **型號及配對仍核對**：完整型號一致、商品外觀符合且配對唯一時，同群同發送者的兩圖兩文交錯、同組中間有影片、或細微時間／seq順序差異可由AI核對來源後通過，不因排列單獨要求人工確認。無型號、不同完整型號、不同發送者、跨日、多張不同合理候選或實質款式衝突仍保留待確認；不能用文字優先把別款圖片配過來。
- **計價單位不能猜**：每個／每套／每雙含糊、價格與裝箱基準矛盾、原文自身衝突、缺少必要成本或費用是否計入未明時，集中詢問。已確認的同款決定沿用；來源實質變動才重開疑點。
- **中間商同貨號不同商品分開建檔**：使用者確認多品村為中間商，不同上游可能使用相同貨號。當來源圖文已核對且明確是不同商品時，保留完整上游原貨號，以品名及我方自有貨號區分、各自建檔；往後不只因上游貨號相同再次詢問。沿用既有內部編號流程及實際保存結果，不推算下一號、不自行為上游貨號加後綴，也不捏造上游身分。同款同來源仍依來源ID、原圖SHA、品名及既有內部貨號查重，不覆蓋既有不同商品。C0008陶瓷碗四件套與路人魚毛絨斜挎包依此分開，四件套16.8元／套、4件／套、20套／箱沿用已確認值。此為業務規則；若現有工具仍只按上游貨號阻擋，記為待解析的技術限制並修復正式查重流程，不偽造貨號或直接繞過查重寫表。
- **只暫緩有疑點商品**：規則未涵蓋的商品自動留在待確認，其餘通過商品連續解析、保存及貼圖；不再要求整日所有例外先回覆，也不每三款或每十款停一次。未回覆的單款不視為通過。
- **技術補件自行續跑**：NAS、上傳或雲表圖片失敗另記待補件，只重試缺少階段，不重複新增商品、不要求使用者再確認同一商品。共通故障集中處理，不能將失敗或雲表預覽宣稱為原圖綁定成功。
- **可直接在對話集中回覆**：使用者可在原對話一次回覆固定規則及少數例外，由AI按來源ID/SHA更新原雲表確認紀錄；回覆入口只是選用方式。每筆保留套用規則版本、原差異、採用值及階段，只有尚未解決的實質疑點留在待確認。

這是 AI 代操作業規範。現有網站沒有獨立的「微信圖文待確認」頁，也沒有自動辨識圖片型號的 OCR／AI 服務；不得把本文件描述成已上線的網站功能或程式硬性攔截。圖片型號由執行者使用可用的看圖能力實際辨識。讀取本文件不擴大本次群組、日期、商品或發送範圍。

## 1. 範圍與原始資料

1. 從 GitHub main 讀取本文件與根目錄 HANDOFF_STATE.md，核對目前工作版本；依使用者指定的群組、日期與數量執行。
   - 使用者後來明確指定略過舊日期、從新起日開始時，以最新範圍決定優先。被略過的原檔、完成項目與歷史核對證據保留；略過不等於完成或核對通過。舊雲表狀態尚未同步時，先讀交接中的有效起日，不能自動把舊待辦重新排入；晚到舊日期資料可下載存檔，但不自行恢復解析。
2. 使用已下載的原始訊息與原圖，保留完整原文、貨號、數量、價格、重量及其他規格。附件下載完成與可開啟後才開始判定；無法看清的字不可補猜。
3. 依同一群組的完整訊息順序核對，保留不同發送者的插話、非商品文字與附件。不能先濾掉聊天，再宣稱圖片和商品文案相鄰。
4. seq 是存檔全域流水號；跨群訊息可能造成跳號。順序判定須核對群組內原始序列、時間與訊息 ID，不能僅測試 seq + 1。
5. 聊天、原圖、確認清單與商品對應是私人作業資料，保存到此工作既有的私人雲端位置；不提交 GitHub，不貼出 Secret、SDK 檔案存取識別或私鑰。保存失敗須回報，不能只留在臨時頁面後宣稱完成。

### 按日整批處理

- **預設一天一批，不固定每三款停下來**：先整理指定廠商群當日全部可取得的原始訊息與附件，完成圖文核對、查重與例外清單。三款小樣只用於初次流程驗證；正常作業由 AI 接續處理全日已通過項目，使用者不必每三款重新下指令。
- **每天 09:00 處理前一天**：排程依台灣時間 `Asia/Taipei` 執行，啟動時固定前一個日曆日為目標，依原始訊息時間 `msgtime` 分日，區間為該日 `00:00` 起至次日 `00:00` 前；不以下載時間分日。例如 10/7 上午處理 10/6。執行跨過午夜時，仍完成原目標日期，不自行擴大範圍。
- **結果標示抓取截止時間**：即使目標日已結束，仍須核對來源缺口，不能僅因下載完成就宣稱整日資料已齊。下一次同步檢查晚到訊息、前次附件失敗與尚未處理項目，按其原始日期補回；無法取得的歷史資料須明列缺口。若另經使用者指定處理當天，只能回報「截至本次抓取」的進度。
- **保留日期邊界上下文**：同群跨午夜的圖文、seq 與訊息時間排序不一致或缺少前後文時，列人工例外。跨日同一組只建立一個配對項目；確認後固定主歸屬日，相鄰日只引用，不新增第二份商品。
- **例外集中一次確認**：先套用已確認固定規則，其餘疑點集中到同一份圖文清單；只暫緩受影響商品，AI連續執行已通過商品。使用者可於原對話集中回覆，後續出現新實質疑點才追加，不按固定款數重複核准，也不因未回覆放行單款。
- **逐款核對、連續執行**：現有工具仍每次保存一款；按日是管理與確認單位，不表示網站已有整日 ZIP 批次匯入功能。沿用逐款來源核對、實際 NO 定位、圖片綁定與重開驗證，不把不同商品混貼進同一表單。
- **每日可安全續跑**：清單保留群組、圖文訊息 ID、原圖 SHA-256、實際 NO 與各階段結果。先核對既有雲端紀錄，再跳過已完成且來源未變的項目；只補失敗或未完成部分。下載水位與商品完成狀態分開記錄，不能只靠最高 seq、日期或圖片摘要判斷已處理。
- **晚到資料改變依據時重新核對**：若新訊息插入先前圖文之間、補充規格或改變配對，受影響項目退回待確認；已入表商品依實際 NO 接續核對或修正，不重建、不直接用於廣告。
- **按日回報**：列出目標日期、抓取截止時間、候選商品數、完成商品數、待確認與待補下載／原文／圖庫／貼圖數，並附原雲表位置。訊息數、附件數與商品數分開，暫緩項目保留在原日期清單。
- **固定雲端確認入口**：原 Google 雲表的「_微信匯入進度」記錄逐日狀態；「_微信確認紀錄」（gid 127501200）是例外資料唯一寫入來源，A:I依序保存項次、日期、文案型號、圖上型號、疑點與来源識別、完整原文、使用者決定、處理狀態、原圖。「_微信待確認」（gid 1683445576）是每日閱讀用動態清單，A3與G3為公式，顯示貨號、圖片、原文、疑點、決定、狀態與回覆入口；禁止直接寫入或清空公式展開區。新增例外及確認回覆只更新確認紀錄；使用群組／圖文訊息ID／SHA核對實際列，不沿用歷史列號，也不能只靠貨號判定同一筆。
- **確認後自動退出清單**：確認紀錄H欄含「已確認」「已完成」「跳過」「不追補」或以「完成」起頭的項目不出現在待確認頁；部分確認、暫緩、待確認及尚未填狀態的有效商品仍保留。空白或部分回覆不等於通過；只有疑點全部解決才改成「已確認／待解析入表」，後续解析完成再更新實際NO與階段。待確認頁G欄連結直達紀錄G:H；確認日期與依據保留於G欄，原文不得覆寫。此為Google Sheets顯示公式，不代表網站新增審核功能。
- **每日清單維護**：追加資料後延伸確認紀錄篩選範圍，核對待確認筆數及目前非空列高度、圖片和文字換行；已解決項目退出後重設多餘空白列高度，不靠持續新增並隱藏列維持待辦。待確認表头凍結前2列，欄寬維持圖文並排。使用者2026-10-11授權從本例外表刪除42筆舊不追補項目，已執行；不要依歷史清單重新加入，也不要據此刪除原始存檔或其他工作表。
- **原圖對照與清單分開驗證**：人工確認須能看到對應原圖，文字清單保存成功不代表原圖已同步。本機圖文對照頁須標明保存範圍；若私人原圖或備份雲端同步受阻，保留原檔並回報，不能只憑雲表清單已保存就宣稱完整備份完成。

2026-10-06 已透過 Codex App 在原工作對話建立並讀回啟用中的每日 09:00 排程，處理前一天多品村資料；首輪排程結果尚待驗證。執行依賴目前電腦的原存檔、可用網路與已登入的操作頁面，電腦及 App 須保持運作。每次先確認單一下載寫入者，不另建重疊 Windows 排程；換電腦先移交資料與排程，避免兩台同時寫入。這項排程不代表網站新增批次匯入功能，也不保證需人工確認或權限受阻的批次會自動完成；阻擋與未同步項目須如實回報，不繞過安全拒絕。

## 2. AI 直接通過條件

以下條件依上方多品村固定決策核對後成立，記錄為「AI 核對通過」或「依文字優先規則核對通過」，不再要求使用者逐款重複確認：

- **圖片型號可辨識且完整**：實際開啟原圖，讀到圖上印刷型號。檔名、圖片排列、文案或上一款型號不能當成圖片辨識結果。
- **型號一致**：圖上型號與原文中明示的完整型號一致。只可統一全半形、大小寫、空白與常見連字號；不得把相近字元、前後綴、部分字串或不同範圍自行當成同一型號。
- **來源與配對明確**：同一群組、同一發送者，完整型號、外觀及上下文支持唯一對應；原始資料沒有影響配對的缺漏。單張圖緊接文案可直接核對；交錯／影片／細微排序差异依固定決策核對，不單憑相鄰位置配圖。
- **配對唯一且商品一致**：同一張圖沒有另一個合理文字候選，品名、款式及可見商品一致。圖文規格差異按文字優先採用並記錄；實質商品身分矛盾不得略過。

這個「通過」只表示此組原圖與原文配對核對完成。成本計算、解析欄位、雲端保存、貼圖位置與後續廣告發送各自仍須核對；不宣稱零錯誤。

## 3. 例外先給使用者確認

以下任一情況記為「待人工確認」：

- 無型號、文字模糊、型號部分可讀、圖與文型號不符。
- 固定決策核對後仍無法唯一配對的先文後圖、多圖多文、多個型號或聊天交錯，以及不同發送者、跨日來源。
- 圖文品名／款式等商品身分衝突、原文自身矛盾、計價基準不明、必要成本缺漏、附件無法讀取或來源缺漏。僅規格差異依文字優先處理，不重複列人工問題。
- 圖片或文案變更，與先前核對的內容不一致。

只把例外整理成對照清單，顯示原圖（可放大）、完整原文、圖上實際讀到的型號、文案型號、原始上下文與具體疑點。介面尚未建置時，由執行者提供原圖文對照檔或可存取的私人雲端對照頁；不得指示使用者尋找不存在的網站按鈕。

使用者可「確認同款」「指定正確圖文配對」或「暫緩／排除」。確認須能對應具體圖片與原文，不把未指明例外項目的「整批通過」當成消除矛盾。保留其確認依據與時間，重新配圖後重新核對；不得替使用者填寫人工確認。附件損壞或來源缺失仍需取得可用原件，不能用一個確認取代資料。

只暫緩未解決例外，已通過商品可立即進入解析；排除項目保留原因、不匯入。不得因等待回覆超時自行通過，也不得以少數未回覆例外阻擋全日進度。

## 4. 每款保留可追溯對應

每款至少記錄：

| 階段 | 必留依據 |
| --- | --- |
| 原始來源 | 群組、發送者、圖片及文字 msgid／seq、來源時間、完整原文、原圖路徑與 SHA-256 |
| 配對 | 圖上實際辨識型號、原文型號、順序／矛盾檢查、AI 通過或人工確認、理由與確認時間 |
| 雲表 | 試算表、分頁、保存後實際 NO、貨號與商品起始列、讀回結果 |
| 貼圖 | 實際使用圖片、原圖摘要、若另製預覽則保留預覽摘要及原圖對應、貼圖位置、重新開啟核對結果 |

SHA-256 用來確保沿用同一張檔案，不能證明圖片與文案是同一商品。來源圖、原文或配對變動時，先前通過失效，重新核對。

## 5. 通過後解析到半自動表

1. 使用既有「報價整理」，每次帶入同一款已通過的完整原文與原圖；逐欄核對解析的貨號、品名、價格、數量、單位、尺寸與重量。配對通過不代表解析內容自動正確。
2. 沿用目前雲端成本參數、重複商品檢查、寫入前後核對及原文保存，不自行推測缺漏欄位或客戶售價。
3. 已存在的商品依 NO、貨號與原文核對後接續未完成階段；不要再按新增。結果不明時先讀回雲表，不能盲目重送。
4. 新增成功後記錄工具實際回傳的分頁、NO 與廠商。現有成功畫面沒有列號，須到原雲表搜尋該 NO，核對貨號、品名與廠商後記錄實際列位置。不得預先假設下一個 NO 或以匯入順序猜列位置。
5. 確認商品原文保存與 NAS 商品圖庫綁定結果；僅圖片失敗時走「商品補圖」，原文失敗時只重試保存原文，不重建商品。

## 6. Computer Use 貼入雲表正確位置

1. 開啟原 Google 雲表，在實際保存的分頁，用 NO 定位商品，重新比對該列品名與貨號；位置變動或 NO 不唯一時停止。
2. 沿用既有商品右側 M:T 圖片區的浮動圖片方式，放在該款六列範圍內。Google 雲表內圖片顯示與 NAS 圖庫綁定是兩個結果，都須各自核對。
3. 每次只取該款已核對的原圖，不依「第幾張圖片」配「第幾列商品」，不沿用未確認內容的剪貼簿。避免遮住報價欄、下一款或更動公式。
4. 若原位已有圖片，先辨識是否同一款；相同則保留，不重複插圖。不同或不確定時停止該款，不能直接覆蓋。
5. 需要相容預覽時，保留原圖並記錄預覽對應。不得改動商品、文字、顏色或款式，也不得稱縮小預覽與原圖位元組相同。
6. 等待雲端保存後，用重新開啟的頁面核對「NO＋貨號＋實際圖片位置與內容」，保存可檢視的對照畫面。不能只憑雲端已儲存圖示或當下看得到圖片，就判定圖片已持久保存。
7. 若上傳逾時或頁面中斷，先重新查明原表是否已有該圖，避免重複插入；只接續缺少部分。
